## دامنه و علت

روی این کمپیوتر سرویس نصب‌شدهٔ AlShifa و `C:\AlShifa\app\appsettings.Production.json` وجود نداشت. MySQL توسعه روی ۳۳۰۷ موجود بود، ولی تست‌ها از آن استفاده نکردند. در `backend/src/AlShifa.Api/appsettings.json`، URL و کلید Sync تنظیم نشده بودند؛ override همان دو گزینه در فرایند بررسی نیز موجود نبود. این علت `Configured=false` در تنظیمات سورس بررسی‌شده است؛ دربارهٔ فرایند ناشناخته یا دستگاه شفاخانه ادعا نمی‌شود.

موارد تأییدشده در دو میزبان:

1. ثبت مریض ساختگی روی API محلی و خواندن همان شناسه و مشخصات از API مستقل آنلاین.
2. ثبت فرمان مریض از آنلاین، اجرای مجاز روی مرجع محلی، تأیید نتیجه و برگشت داده به آنلاین.

4. ارسال دوبارهٔ درخواست مریض، پرداخت و فاکتور بدون ردیف اضافی؛ مبلغ پرداخت ۶۰ مصنوعی در هر دو طرف فقط یک‌بار ثبت شد؛ دفتر مالی متوازن ماند.

6. صف محلی در پایان خالی، شناسهٔ منبع مقصد مطابق هویت همان نصب آزمایشی، رمز محلی حفظ‌شده و دفتر مالی متوازن بود.

## نصب نهایی و مرز تأیید

هیچ ارتقا، migration یا enrollment روی دیتابیس اصلی Contabo انجام نشده است. مقصد موجود نباید با دیتابیس دفتر جایگزین، reset یا بدون تطبیق به شناسهٔ دفتر متصل شود. دادهٔ ساختگی دفتر برای پذیرش آزمایشی است و نباید به دیتابیس اصلی منتقل شود.

برای نصب واقعی، نسخه و تنظیمات مؤثر دستگاه شفاخانه باید خوانده شود؛ بکاپ داده/فایل/هویت با بازیابی جداگانه اثبات شود؛ اختلاف schema و تاریخچهٔ sync تطبیق یابد؛ نسخهٔ مشترک مورد تأیید ابتدا آنلاین و سپس محلی نصب شود؛ source enrollment مقصد موجود با تأیید مالک انجام شود. برداشتن hold فقط پس از این بررسی است. تغییر حساس سرور اصلی طبق درخواست کاربر به تأیید جداگانه نیاز دارد.

مسیر برعکس به معنی صف فرمان آنلاین و اجرای مجاز روی دیتابیس محلی مرجع است؛ ادغام دو دیتابیس مستقل نیست. پس از provisioning و فعال‌سازی، worker باید بدون کار روزانهٔ کارمند retry کند؛ تأیید ارتقای بعدی یا تعارض داده همچنان فرایند مدیریتی است.
